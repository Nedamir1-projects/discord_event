# ТЗ на тестирование платформы Discord Bots

## 1. Назначение и границы

Документ задаёт полный план функционального, интеграционного, регрессионного и безопасностного тестирования текущего монорепозитория `discord-bots-platform`:

- **Economy Bot** — конфеты, профиль, магазин, расы, способности, активность, «Ночь охоты», «Проклятие Хэллоуина», тыквы.
- **Event Master** — `/panel`, текстовые команды администратора, управление событиями и «Судной ночью», снимки состояния, восстановление, роли и игровые каналы.
- **`packages/shared`** — PostgreSQL/Prisma, общая экономика, операции событий, идемпотентность, журналирование и конфигурация.

План рассчитан на текущую реализацию. Тесты должны подтверждать поведение кода, а не предполагать наличие функций, которых в проекте нет. В частности, для «Судной ночи» `/matrixrename`, `/matrix_avatar`, `/matrix_law`, автоматическое распределение всех участников случайным образом и отмена сообщений в Чистилище не являются частью проверяемого текущего функционала. Их нельзя отмечать как пройденные без отдельной реализации.

## 2. Цели тестирования

1. Проверить, что разрешённые пользователи могут выполнить нужные операции, а остальные получают отказ и не меняют данные.
2. Проверить баланс, цены, награды, списания, повторы и параллельные запросы без потери или дублирования конфет.
3. Проверить жизненные циклы трёх событий и восстановление после перезапуска или частичного сбоя Discord API.
4. Проверить соответствие Discord-ролей, прав каналов и записей участников в PostgreSQL.
5. Проверить приватность ответов, секретных ролей, игровых журналов и конфиденциальных значений.
6. Проверить валидацию конфигурации, миграции, регистрацию slash-команд и корректное завершение процессов.

## 3. Тестовые среды и данные

### 3.1 Среды

Использовать отдельный тестовый Discord-сервер и отдельную тестовую PostgreSQL-базу. Slash-команды регистрировать только в тестовом `GUILD_ID`. Не запускать сброс данных на рабочем сервере. Для автоматизированных тестов Discord API подменять адаптерами и заглушками; живые Discord API проверки выполнять только вручную на тестовом сервере.

Рекомендуемые среды:

| Среда | Назначение | Условия |
|---|---|---|
| Unit | Правила, валидация, политика доступа | Без Discord и без общей базы |
| Integration | Prisma, транзакции, миграции, восстановление | Отдельная временная PostgreSQL |
| Discord sandbox | Slash-команды, интеракции, роли, права каналов | Тестовый сервер, тестовые боты |

### 3.2 Аккаунты

Подготовить как минимум следующие Discord-аккаунты:

| Код | Настройка | Для чего |
|---|---|---|
| `ADMIN_A` | ID включён в `ADMIN_IDS` | Разрешённый администратор |
| `ADMIN_B` | ID включён в `ADMIN_IDS` | Второй администратор, проверка чужой панели |
| `USER` | Обычный участник | Обычные команды и запрет админских действий |
| `WITCH` | Раса Witch в БД | Проверка проклятия и текстового бонуса |
| `WEREWOLF` | Раса Werewolf в БД | Проверка голосового множителя |
| `VAMPIRE` | Раса Vampire в БД | Проверка укуса |
| `GHOST` | Раса Ghost в БД | Проверка вселения |
| `MATRIX_PUNISHER` | Участник Matrix с ролью Punishers | Jail |
| `MATRIX_REBEL` | Участник Matrix с ролью Rebels | Unjail, прогресс миссии |
| `MATRIX_PROPHET` | Участник Matrix с ролью Prophet | Проверка отсутствия несуществующих полномочий |
| `MATRIX_PRISONER` | Участник Matrix с ролью Prisoners | Проверка изоляции и запретов |
| `BOT_ACCOUNT` | Другой Discord-бот | Исключение ботов из фарма и тест целей способностей |

`ADMIN_A` и `ADMIN_B` должны иметь обычные Discord-роли без права Administrator для проверки, что доступ определяется именно `ADMIN_IDS`. Отдельно проверить ошибочную конфигурацию, где администратор Discord не включён в `ADMIN_IDS`, и обратный случай — ID в `ADMIN_IDS` без роли администратора Discord.

### 3.3 Наборы данных

- Тестовый баланс: 0, ровно стоимость товара/расы, на 1 меньше стоимости, большой допустимый баланс.
- Расы: Mortal, Witch, Werewolf, Vampire, Ghost с контрольными ценами из конфигурации/каталога.
- Активности: сообщения обычные, пустые, повторяющиеся, команды, сообщения ботов; голосовой онлайн в разрешённом, неразрешённом и AFK-каналах.
- Ивенты: draft/waiting, active/running, paused, completed/ended; просроченный и будущий дедлайн.
- Matrix-сервер: участники с исходными ролями, включая несколько постоянных ролей, участника с нулём ролей, владельца сервера, бота, участника вне события и роли выше бота.
- Тыквы: зарегистрированная ссылка и корректное сообщение, неверный сервер/канал/автор/содержимое, удалённое сообщение, закрытый канал.

## 4. Общие правила выполнения и регистрации результата

Каждый сценарий получает ID, например `AUTH-01`, и записывается в отчёт со статусом `PASS`, `FAIL`, `BLOCKED` или `NOT RUN`. Для каждого запуска указывать commit/build, среду, дату UTC, исполнителя, тестовые ID событий и краткое доказательство (лог, скриншот, SQL-проверка). Не включать в доказательства токены, пароли, `DATABASE_URL` и другие секреты.

При каждом отказе проверять не только текст ответа, но и то, что:

- исходный баланс, роли, состояние события и прогресс не изменились;
- не создана успешная транзакция или запись прогресса;
- если операция должна попасть в аудит/журнал ошибок — записаны actor, действие, объект, UTC-время, результат и причина;
- Discord interaction получила ответ вовремя, без необработанной ошибки «This interaction failed».

## 5. Матрица доступа и полномочий

### 5.1 Политика

В проекте главный источник разрешения админских команд — Discord ID из `ADMIN_IDS`, а не название или позиция Discord-роли. Исключение — ограниченная команда полного сброса, которая дополнительно доступна только настроенному в проекте владельцу сброса. Игровые команды Матрицы поверх Discord-авторизации проверяют запись участника и фракцию в Matrix-событии. Проверка только видимости кнопки недостаточна: прямой вызов команды/устаревшего component ID также должен быть запрещён.

| Операция | Разрешённый субъект | Обязательные отрицательные проверки |
|---|---|---|
| Пользовательские `/balance`, `/profile`, `/shop`, `/race`, `/abilities`, `/leaderboard` | Любой пользователь сервера | Не менять чужие данные; скрывать личный баланс в ephemeral-ответе |
| `/bite` | Участник, прошедший проверку расы/правил способности в сервисе | Mortal/Witch/Ghost/бот/сам пользователь/невалидная цель/КД не должны дать несанкционированный перевод |
| `/curse` | Witch согласно правилам сервиса | Не-Witch, цель-бот, повтор/КД и невалидная цель — отказ без побочного эффекта |
| `/possess` | Ghost согласно правилам сервиса | Не-Ghost, запрещённая цель, повторная/несовместимая способность — отказ |
| `/hunt join`, `/hunt status`, `/hunt attack` | Участники, для атаки — участник события по правилам боя | Нет события, неверная фаза, неверное действие, повтор interaction, неучастник |
| `/halloween` пользовательские подкоманды | Участник текущей кампании; join регистрирует участника | Неактивная кампания, закрытая/неизвестная загадка, повторный reward/vote, зависимый квест |
| `/pumpkin` | Пользователь с валидной ссылкой на зарегистрированный пост | Невалидная ссылка, неверный guild/channel/author/content, повторное получение |
| `/panel` и все admin panel components | ID из `ADMIN_IDS` и владелец живой сессии панели | Незарегистрированный ID, чужой session ID, устаревшая сессия, изменённый custom ID |
| Admin prefix-команды Event Master | ID из `ADMIN_IDS` | Обычный участник, бот, неверный префикс/аргументы |
| Полный factory reset | Только специальный владелец сброса, с подтверждением | Другой `ADMIN_IDS`, обычный пользователь, отсутствие/неверное подтверждение |
| `/matrix create/assign/start/pause/resume/emergency/mission_create/outcome/list` | ID из `ADMIN_IDS` | Неадмин и Discord-администратор без `ADMIN_IDS` должны получить отказ |
| `/matrix jail` | Участник активной Matrix-игры с ролью Punishers | Rebels/Prophet/Prisoners/неучастник/пленный актор/неверный сервер |
| `/matrix unjail` | Участник активной Matrix-игры с ролью Rebels | Punishers/Prophet/Prisoners/неучастник/пленный актор/неверный сервер |
| Кнопка «Продвинуть» в `#миссии` | Участник активной игры с ролью Rebels и незаключённый | Punishers/Prophet/Prisoners/неучастник/пленный/не та фракция/пауза; вклад вводится через modal |
| Discord роль/каналы Matrix | Event Master с нужными `Manage Roles`/`Manage Channels` и корректной иерархией | Нет permission, роли выше бота, отсутствующий ресурс — операция не объявляется полной |

### 5.2 Сценарии авторизации

- `AUTH-01`: каждый slash-админский маршрут вызвать как `ADMIN_A`; ожидается выполнение после валидной подготовки.
- `AUTH-02`: повторить каждый admin route пользователем `USER`; ожидать отказ, отсутствие мутаций, приватное понятное сообщение.
- `AUTH-03`: вызвать тот же маршрут Discord-пользователем с Discord Administrator, но без ID в `ADMIN_IDS`; отказ.
- `AUTH-04`: вызвать админ-команду пользователем из `ADMIN_IDS` без Discord Administrator; если код использует allowlist, команда проходит авторизацию приложения, но любые Discord API действия отдельно проверяют фактические Discord permissions.
- `AUTH-05`: открыть `/panel` как `ADMIN_A`, скопировать component ID и вызвать его как `USER` и `ADMIN_B`; оба чужих пользователя не должны применить действие.
- `AUTH-06`: вызвать кнопку панели после истечения TTL; сообщение об устаревшей панели, мутаций нет.
- `AUTH-07`: нажать подтверждение опасной операции без предварительного запроса/в другой сессии; отказ.
- `AUTH-08`: выполнить Factory Reset как `ADMIN_A`, если он не специальный владелец; отказ даже при корректном подтверждении.
- `AUTH-09`: выполнить Factory Reset как специальный владелец без подтверждения и с неверным текстом подтверждения; сброс не выполняется.
- `AUTH-10`: Matrix-участник одной фракции пытается выполнить команду другой фракции; отказ на сервисном уровне, даже если Discord-права канала ошибочно разрешают действие.

## 6. Запуск, конфигурация, миграции и команды Discord

- `BOOT-01`: корректная конфигурация загружает Economy Bot без секретов Event Master и Event Master без секретов Economy Bot.
- `BOOT-02`: отсутствие обязательного token/client ID/валидного `DATABASE_URL` останавливает запуск с перечислением отсутствующих имён полей; значения секретов в логе отсутствуют.
- `BOOT-03`: проверить границы и формат `GUILD_ID`, `ADMIN_IDS`, префикса, allowlist каналов, интервалов и лимитов активности.
- `BOOT-04`: `TIMEZONE` корректно применяется к расчёту ночного бонуса, включая переход через полночь и смену календарной даты.
- `BOOT-05`: применить все Prisma migrations на пустой тестовой базе; повторное применение не портит данные и не создаёт дубликаты.
- `BOOT-06`: запустить оба бота с одной БД; конфликта миграций, одновременной инициализации Prisma и несовместимых записей нет.
- `BOOT-07`: `npm run build`, `npm run typecheck`; зарегистрированные команды сериализуются Discord API schema validator без ошибок обязательных параметров, ограничений и локализаций.
- `BOOT-08`: регистрация команд в тестовом guild создаёт ожидаемый список обоих приложений; повторная регистрация идемпотентна, не стирает команды другого приложения.
- `BOOT-09`: неверные Discord token/client ID и временная недоступность Discord API дают понятный безопасный лог и корректный ненулевой статус, если регистрация не удалась.
- `BOOT-10`: SIGINT/SIGTERM закрывает Discord gateway и Prisma; повторный запуск не оставляет зависших соединений/дублирующих фоновых задач.

## 7. Общая экономика и профиль игрока

### 7.1 Баланс, транзакции, история

- `ECO-01`: новый участник получает профиль с ожидаемыми стартовыми значениями и расой Mortal.
- `ECO-02`: `/balance` показывает текущий баланс и последние операции; `/profile` согласован с тем же балансом и текущей расой.
- `ECO-03`: проверить положительное начисление, отрицательное списание, нулевую/невалидную сумму, нижнюю границу 0 и верхнюю границу типа БД.
- `ECO-04`: списание суммы, равной балансу, успешно; на 1 больше — отказ, баланс не уходит в минус.
- `ECO-05`: повтор операции с тем же `operationId` не меняет баланс повторно; операция с новым ID выполняется отдельно.
- `ECO-06`: две конкурентные операции списания, каждая из которых отдельно допустима, не создают отрицательный баланс и не теряют журнал.
- `ECO-07`: при падении/ошибке между транзакционными шагами баланс и BalanceTransaction остаются согласованными.
- `ECO-08`: история отражает правильный знак суммы, источник/причину и UTC-время, не содержит чужих записей.
- `ECO-09`: leaderboard сортирует по фактическому балансу; одинаковые значения обрабатываются стабильно; форматирование не ломается на пустой таблице и длинном списке.

### 7.2 Магазин и покупка

- `SHOP-01`: `/shop` показывает до пяти товаров на странице, кнопки выбирают правильный товар, стрелки листают страницы; пустой каталог обрабатывается корректно.
- `SHOP-02`: покупка кнопкой за достаточный баланс списывает правильную сумму и сохраняет покупку; товар с ролью проверяет и выдаёт привязанную роль.
- `SHOP-03`: количества 1 и верхняя граница допустимого количества работают; 0, отрицательное, дробное, сверх лимита и неизвестный товар отклоняются.
- `SHOP-04`: недостаточный баланс отклоняет всю покупку; нет частичного списания или Purchase.
- `SHOP-05`: повтор одного Discord interaction/operation ID не списывает повторно.
- `SHOP-06`: две параллельные покупки при балансе, достаточном только для одной, дают максимум одну успешную покупку.
- `SHOP-07`: для товара с ограничениями ивента проверить покупку до/после окна события и смены статуса; поведение должно соответствовать настройке товара.
- `SHOP-08`: ошибка внешнего Discord-действия после покупки (если оно настроено) отображается как частичный результат, финансовая запись остаётся аудируемой и не повторяется без новой операции.

### 7.3 Покупка расы и Discord-роли

- `RACE-01`: `/race` без параметра показывает доступные расы и фактические цены.
- `RACE-02`: Mortal/каждая доступная раса приобретается при достаточном балансе; цена списывается ровно один раз, profile отражает расу.
- `RACE-03`: недостаточно конфет, неизвестная раса, повторная покупка запрещённой расы/покупка вне разрешённого дня отклоняются согласно правилам сервиса.
- `RACE-04`: повтор одного operation ID не списывает цену повторно.
- `RACE-05`: при привязанных Hunt Discord-ролях новая роль выдаётся, старая event-раса удаляется, прочие постоянные роли не трогаются.
- `RACE-06`: при отсутствии `Manage Roles`, удалённой роли или роли выше бота пользователь получает сообщение о частичном применении: покупка/сохранённая раса и отказ Discord-роли не должны сообщаться как полное Discord-успешное завершение.
- `RACE-07`: без соответствующего текущего Hunt события или на другом guild покупка не изменяет Discord роли другого сервера.
- `RACE-08`: проверить одновременную покупку двух рас двумя взаимодействиями пользователя; конечная запись и набор event-ролей должны быть согласованы без двойного списания.
- `RACE-09`: перед стартом Hunt и после него покупка Witch/Werewolf/Vampire/Ghost работает только при достаточном балансе; расовая Discord-роль заменяет Mortal/предыдущую расовую роль, а не складывается с ней.
- `RACE-10`: покупка Mortal за 0 конфет после старта (если Race доступна в каталоге) не должна снимать другие постоянные роли; повтор текущей расы возвращает `У вас уже выбрана эта раса.` без транзакции.

## 8. Фарм активности и фильтры антифарма

### 8.1 Текст

- `ACT-TXT-01`: учитываются только сообщения подходящих пользователей и разрешённых каналов согласно настройке `TEXT_CHANNEL_IDS`.
- `ACT-TXT-02`: бот, сообщение без guild, пустое сообщение, slash/prefix-команда, неразрешённый канал не дают прогресс.
- `ACT-TXT-03`: достижение порога `TEXT_REWARD_EVERY` выдаёт ровно `TEXT_REWARD_CANDIES`; недобор порога награды не даёт.
- `ACT-TXT-04`: Witch получает настроенный бонус +15% (или актуальный коэффициент конфигурации) с ожидаемым округлением; Mortal/прочие расы — базовую сумму.
- `ACT-TXT-05`: проверить минимальный интервал, повторяющиеся сообщения, предел в час и окно повторов: заблокированное сообщение не наращивает счетчик/баланс.
- `ACT-TXT-06`: удалить/редактировать уже учтённое сообщение не позволяет повторно фармить или повторно начислить награду.
- `ACT-TXT-07`: переключение расы между сообщениями применяет бонус именно по правилу расчёта (в момент сообщения или выплаты — зафиксировать текущее ожидаемое поведение).
- `ACT-TXT-08`: параллельные сообщения около порога не теряют прогресс и дают только одну выплату за каждый достигнутый блок.

### 8.2 Голос

- `ACT-VOICE-01`: вход в разрешённый voice channel создаёт/обновляет время сессии; выход закрывает сессию и сохраняет прогресс.
- `ACT-VOICE-02`: начисление происходит за каждые полные интервалы, неполный остаток сохраняется по правилам сервиса.

## 9. Способности рас (Economy Bot)

Для каждого теста проверять роль/расу владельца способности в профиле, цель, кулдаун, эффект/транзакции, повтор, self-target, bots и права Discord. Названия команд в проекте: `/bite`, `/curse`, `/possess`.

- `ABILITY-01 Bite success`: Vampire применяет укус к допустимой цели; сумма в пределах настроенного лимита списывается у цели и начисляется владельцу; две записи финансовой истории связаны с одной операцией.
- `ABILITY-02 Bite forbidden actor`: не-Vampire вызывает `/bite`; отказ без переводов и без старта кулдауна.
- `ABILITY-03 Bite target rules`: проверить себя, бота, участника без профиля, нулевой баланс, цель не Mortal/цель другой расы и отсутствующую цель; результат соответствует текущим правилам сервиса, баланс не становится отрицательным.
- `ABILITY-04 Bite cooldown`: повтор раньше 4 часов (если текущая настройка 4h) отклоняется; после истечения разрешён; параллельные клики не обходят кулдаун.
- `ABILITY-05 Bite idempotency`: повтор одного interaction ID не переводит конфеты дважды.
- `ABILITY-06 Curse success`: Witch применяет curse; GameEffect/AbilityCooldown сохраняются, срок эффекта соответствует одному часу, цель получает настроенный временный статус/роль.
- `ABILITY-07 Curse forbidden actor`: не-Witch и неучастник не могут применить способность; нет эффекта или кулдауна.
- `ABILITY-08 Curse restrictions`: цель Witch с иммунитетом, сам Witch, бот, повторная цель/эффект проверяются по текущей реализации и требованиям; не возникает двойная/залипшая роль.
- `ABILITY-09 Curse expiry/restart`: эффект истекает автоматически или через recovery после перезапуска; исходное состояние роли сохраняется (роль, бывшая у цели до эффекта, не удаляется ошибочно).
- `ABILITY-10 Possess success`: Ghost применяет эффект длительностью 30 минут; GameEffect фиксирует владельца, цель и срок; применённое визуальное Discord-состояние восстанавливается.
- `ABILITY-11 Possess forbidden actor/target`: не-Ghost, бот или запрещённая цель не меняют данные и Discord.
- `ABILITY-12 Concurrent effects`: повторное наложение того же эффекта, разные эффекты на одной цели, истечение старого после нового не удаляют роль/состояние, принадлежащее другому эффекту.
- `ABILITY-13 Role permission failure`: нет `Manage Roles`, цель покинула guild, роль не найдена или выше бота; оператор получает ограниченное сообщение, ошибка не раскрывает секреты и операция не считается полностью применённой.
- `ABILITY-14 Recovery`: после перезапуска просроченные GameEffect обрабатываются один раз, незавершённые роли восстанавливаются; повтор recovery безопасен.

> Если конкретная механика из старого описания (например, таймер curse раз в сутки, иммунитет вампира к проклятию, блокирование emoji/reactions) не подтверждена текущей реализацией, её следует завести как отдельный acceptance requirement и не считать покрытой только наличием slash-команды.

- `MAT-26`: запрещено арестовать самого себя, бота, пользователя вне этого события или цель на другом guild; причина обязательна, пустые пробелы отклоняются.
- `MAT-27`: duration равна максимуму — разрешено; выше максимума, 0, отрицательное и сверх диапазона — отказ без записи успешного ареста.
- `MAT-28`: второй jail того же target, повтор interaction ID и конкурентный jail двумя Punishers не создают несколько конфликтующих активных заключений.
- `MAT-29`: Discord role update проходит частично: запись результата каждого изменения видна; неуспешная выдача Prisoner role не отмечается как успешное заключение.
- `MAT-30`: успешно посаженный участник перестаёт выполнять mission и jailed actor не может использовать jail/unjail.
- `MAT-31`: Rebel выполняет `/matrix unjail` активного заключённого; восстанавливается корректная event role/исходная роль согласно снимку и состоянию других активных заключений; журнал обновлён.
- `MAT-32`: unjail несуществующего/уже освобождённого пользователя, не-Rebel, неактивное событие и повтор operation ID безопасно отклоняются/возвращают duplicate.
- `MAT-33`: истечение jail и восстановление после перезапуска освобождают участника один раз и сохраняют исходные постоянные роли.

### 12.4 Миссии и фракционные права

- `MAT-34`: администратор создаёт mission с названием, описанием, фракцией, целью и следствием; невалидная цель/faction отклоняется.
- `MAT-35`: Rebels продвигают доступную им mission положительным amount; прогресс не превышает допустимую цель без корректной обработки, completion фиксируется один раз.
- `MAT-36`: Punisher/Prophet/Prisoner/неучастник пытаются продвинуть mission — отказ без `MatrixMissionAction` и изменения прогресса.
- `MAT-37`: миссия не той фракции, закрытая/несуществующая mission, paused/ended event, незаключённая фаза и jailed participant обрабатываются верно.
- `MAT-38`: повтор interaction ID и одновременный progress не дублируют действие, не теряют increments и не завершают миссию дважды.
- `MAT-39`: endpoint outcome записывает actor, результат и audit; повторная фиксация результата не перезаписывает историю неожиданно.

### 12.5 Пауза, завершение, аварийное восстановление

- `MAT-40`: pause при активном событии сохраняет оставшееся время; игровая миссия/jail запрещены или допускаются ровно согласно бизнес-правилу (ожидаемая политика зафиксирована в acceptance); нельзя вызывать resume для неприостановленного.
- `MAT-41`: resume продолжает оставшееся время, а не обнуляет таймер; повтор resume/pause не сдвигает дедлайн лишний раз.
- `MAT-42`: `/matrix emergency` без точного подтверждения не изменяет роли; неверный event ID/сервер/actor отклоняется.
- `MAT-43`: успешное emergency завершает event, восстанавливает исходные роли участников и состояние snapshot; реальная история финансов не удаляется.
- `MAT-44`: один Discord API вызов падает при restore: остальные участники обрабатываются, по каждой операции фиксируется complete/skipped/failed, snapshot остаётся partial, можно повторить recovery.
- `MAT-45`: ошибка во время выдачи игровых ролей после успешного снятия исходных ролей; операция не объявляется успешной, журнал показывает точный этап, повторная попытка идемпотентна.
- `MAT-46`: перезапустить Event Master во время countdown, active, pause и partial restore; на старте recovery возобновляет незавершённое без повторного изменения уже восстановленных ролей.
- `MAT-47`: два одновременных старта/завершения/аварийного восстановления для одного event блокируются/сериализуются, snapshot lock не допускает двойной restore.
- `MAT-48`: «Удаление событий/ролей/каналов» при сбросе удаляет только provisioning resources, перечисленные для этого event; ошибки удаления отражаются по каждому объекту, данные не очищаются при незавершённой очистке.
- `MAT-49`: `/matrixrename`, `/matrix_avatar`, `/matrix_law` не должны регистрироваться как доступные обработчики и не должны менять guild.

## 13. Административная панель Event Master

### 13.1 Сессия и интерфейс

- `PANEL-01`: `/panel` как `ADMIN_A` показывает четыре раздела: Hunt, Halloween, Matrix, Control Center.
- `PANEL-02`: обычный пользователь не может открыть панель; ответ ephemeral; сессия не создаётся.
- `PANEL-03`: навигация между разделами и «Назад» обновляет исходное сообщение, не плодит новые публичные сообщения.
- `PANEL-04`: custom ID кнопки содержит сессию/действие; пользователь не может подменить ID/selected ID и выполнять операции для другой сессии.
- `PANEL-05`: устаревшая кнопка, отсутствующий event, invalid select value, повторное нажатие после удаления/редактирования сообщения дают аккуратное сообщение Discord interaction error.
- `PANEL-06`: длинные списки участников/логов/событий не превышают embed/component limits; пагинация или обрезка сохраняет корректную сортировку.
- `PANEL-07`: все sensitive ответы ephemeral; пользователь панели не раскрывается другому участнику.

### 13.2 Hunt/Halloween/Matrix управление

- `PANEL-08`: создать событие через панель, заполнить модальные поля; корректная валидация и повторное открытие показывают сохранённые значения.
- `PANEL-09`: значения пустые, слишком длинные, неверный числовой диапазон, неправильный тип event или дубликат — не сохраняются; форма остаётся понятной.
- `PANEL-10`: запуск, пауза, resume, завершение для каждого типа события используют собственные сервисы и не меняют статус другого ивента.
- `PANEL-11`: завершение, reset прогресса, запуск боя и массовые изменения требуют confirm/cancel; cancel не меняет систему; подтверждение из той же сессии выполняет ровно один раз.
- `PANEL-12`: изменения настроек, создание chapter/riddle/quest/poll/traitor/тыквы, boss config, rewards сохраняются и отображаются после reload.
- `PANEL-13`: настройки Hunt не изменяют Halloween/Matrix; настройки Halloween не меняют Hunt; подтверждение отдельной операции не перепутывается с другой ожидающей операцией.
- `PANEL-14`: Matrix roster отображает участников и миссии с актуальными ролями/progress; длинный roster не ломает embed.

### 13.3 Игроки, финансы и журналы

- `PANEL-15`: поиск профиля игрока показывает только целевого пользователя; неверный ID возвращает безопасную ошибку.
- `PANEL-16`: администратор вручную начисляет/снимает конфеты; валидная операция идёт через общий economy service и записывает actor/action/reason.
- `PANEL-17`: отрицательное/нулевое/небезопасно большое начисление и снятие большего остатка отклоняются.
- `PANEL-18`: журнал действий и ошибок показывает UTC-время, актёра, действие, event/object, outcome, operation ID и безопасные подробности.
- `PANEL-19`: поиск/фильтры по периоду/типу события/администратору/статусу дают соответствующую выборку; границы периода inclusivity согласованы.
- `PANEL-20`: статистика Control Center показывает период; не смешивает показатели семантически разных ивентов и отображает награды по финансовому ledger.
- `PANEL-21`: error log не выводит bot tokens, пароли, URL подключения или секреты даже если ошибка содержит входные данные.
- `PANEL-22`: последняя административная операция отображается в правильном порядке и при совпадающем времени имеет детерминированную сортировку.

## 14. Текстовые команды Event Master и сброс

Префикс берётся из конфигурации; проверить `<` и поддерживаемый альтернативный `>`.

- `PREFIX-01`: `<help` показывает справку; неправильное число аргументов и неизвестная команда возвращают usage/отказ, не меняют БД.
- `PREFIX-02`: `<events` показывает список событий и отправляет личный ответ; пользователь без DM-доставки получает понятное сообщение без падения handler.
- `PREFIX-03`: `<event start|pause|resume|end ID` создаёт подтверждение опасных переходов, соблюдает state machine и пишет AuditLog.
- `PREFIX-04`: `<give DISCORD_ID amount` / `<take DISCORD_ID amount` выполняются только разрешённым ID; проверяются формат ID, положительная безопасная сумма, баланс и дублирование message ID.
- `PREFIX-05`: `<stats`, `<logs [count]` ограничивают размер результата, корректно работают на пустой базе и фильтруют данные.
- `PREFIX-06`: все команды как `USER` отвергаются; пользовательский текст, похожий на команду, но без префикса/точного имени не обрабатывается.
- `PREFIX-07`: сообщения от bot accounts и сообщения в DM не запускают админские команды/фарм.
- `RESET-01`: запрос `<reset` доступен только специальному reset owner, создаёт confirm/cancel; cancel сохраняет все данные.
- `RESET-02`: подтверждённый reset удаляет только provisioned roles/channels/categories и event/game progress, показывает количество успешных/неуспешных удалений.
- `RESET-03`: reset не удаляет BalanceTransaction/финансовую историю, не удаляет чужие Discord ресурсы и не затирает конфигурацию/посторонние event роли.
- `RESET-04`: Discord cleanup failure — БД не сбрасывается как будто всё успешно; частичный результат позволяет повторить безопасное завершение.
- `RESET-05`: double-confirm и повторная доставка одного custom ID не удаляют ресурсы дважды и не дают ошибку целостности.
- `RESET-06`: **Известное расхождение текущего кода с требованием:** `resetAllGameData` удаляет `BalanceTransaction` и `AuditLog`, хотя финансовая история должна сохраняться. Прогон подтвердит дефект (ожидаемый по ТЗ результат — история и аудит сохранены); до исправления сценарий отмечать `FAIL`, не подменять ожидаемый результат текущим поведением.

## 15. PostgreSQL, устойчивость и аудит

- `DB-01`: проверить ограничения уникальности (пользователь/ивент/slot/голос/operation ID), внешние ключи и каскады на каждом типе сущностей.
- `DB-02`: отключить БД до команды: бот возвращает безопасную ошибку, не отправляет ложный success, не пишет секреты в logger.
- `DB-03`: разорвать соединение во время transaction; после восстановления нет частично начисленного баланса или дублированной операции.
- `DB-04`: перезапустить оба процесса после создания профиля, покупки, активности, события, vote, pumpkin find, Matrix snapshot/jail; состояние сохраняется.
- `DB-05`: миграция с предыдущей поддерживаемой схемы сохраняет финансовые, пользовательские и event данные.
- `DB-06`: AuditLog создаётся для критических действий: запуск/пауза/завершение/сброс, выдача/списание средств администратором, изменения событий и Matrix role/snapshot/recovery.
- `DB-07`: в AuditLog actor ID, action, object type/ID, result, details и timestamp правильные; результат partial/error нельзя записать как success.
- `DB-08`: операции не сохраняют токены, пароли, полный `.env`, приватное содержимое, не относящееся к аудиту.
- `DB-09`: проверить UTC-хранение timestamp и формат отображения в Discord с unix timestamp/UTC; timezone хоста не меняет persisted instant.
- `DB-10`: параллельные Economy Bot и Event Master действия к одному PlayerProfile не перезаписывают друг друга и не создают отрицательный баланс.

## 16. Discord API, каналы, роли и частичные сбои

- `DISCORD-01`: для provisioning проверить `ManageRoles` и `ManageChannels` до изменения; отсутствие нужного права отображается конкретно.
- `DISCORD-02`: проверить role hierarchy для создания/выдачи/удаления; бот не меняет роли выше своей highest role.
- `DISCORD-03`: все event roles не имеют Administrator; Event Master и Economy Bot также работают без Administrator.
- `DISCORD-04`: удалить роль/канал вручную в процессе события; последующая команда сообщает о недостающем объекте и не падает целиком.
- `DISCORD-05`: Discord API возвращает 403, 404, 429, timeout, gateway reconnect; retry соблюдает rate limits, duplicate operation не создаётся.
- `DISCORD-06`: в массовой операции первый, средний или последний элемент падает; результат каждого элемента сохраняется, UI показывает total/success/skipped/failure и причины.
- `DISCORD-07`: проверять category permission inheritance плюс explicit channel overwrites; запрет `@everyone` нельзя случайно открыть через allow на другом role.
- `DISCORD-08`: после provision/reset сверить set IDs из БД с реальными ресурсами, а не только похожими названиями.
- `DISCORD-09`: interaction response/defer/editReply выполнены в допустимое время; исключения после defer/edit корректно редактируют сообщение или отвечают follow-up.
- `DISCORD-10`: устаревшие компоненты и удалённое исходное сообщение не порождают необработанный rejection в процессе Node.

## 17. Наблюдаемость и приватность

- `OBS-01`: при старте каждый бот пишет готовность, подключение БД и статус; health check не раскрывает секреты.
- `OBS-02`: для ошибки логировать тип ошибки, operation ID/event ID (если есть), этап и ограниченную причину; не писать stack/input secrets в пользовательский ответ.
- `OBS-03`: каждому interaction reply соответствует понятный пользовательский результат: success, duplicate, validation error, permission denied, partial failure или retry pending.
- `OBS-04`: личный баланс, тайная роль Halloween, административные логи и результаты управления отправляются только нужному пользователю (ephemeral/DM с корректной обработкой отказа).
- `OBS-05`: проверить запрет массового mention `@everyone` во всех текущих обработчиках, кроме явно реализованного и разрешённого требования; Matrix law-команда сейчас не входит в функциональную поверхность.
- `OBS-06`: сообщения Discord, guild/member/channel ID и operation ID в журналах достаточно для поддержки, но не содержат credentials.

## 18. Нефункциональные проверки

- `NFR-01 Capacity`: тестовый сервер с большим количеством участников; roster, лидерборд, события и логи не выходят за лимиты Discord embeds/components.
- `NFR-02 Rate limit`: массовое Matrix role assignment/restore проверяется на очереди, соблюдении Discord 429 retry-after и отсутствии параллельного лавинообразного повторения.
- `NFR-03 Concurrency`: одновременно отправить операции на один профиль/один vote/один pumpkin slot/одну jail/одну mission; итог соответствует ограничениям уникальности и балансам.
- `NFR-04 Recovery`: аварийно завершить процесс в точках до/после DB commit и до/после Discord API; после перезапуска операция либо безопасно продолжается, либо отображается как partial, но не объявляется незаметно завершённой.
- `NFR-05 Compatibility`: текущая версия Node 24.x, npm 11+, установленная версия Discord.js, PostgreSQL из compose и целевая продовая PostgreSQL.
- `NFR-06 Localization`: имена slash-команд и options проходят требования Discord к ASCII name, ограничения длины и сериализацию; русская локализация не повреждена mojibake и доступна в Discord client locale.
- `NFR-07 Stability`: длительный прогон голосовых/текстовых событий и фонового recovery не создаёт накапливающиеся listeners, tasks, Prisma connections или memory growth.

## 19. Автоматизация и уровни покрытия

### Unit

Обязательные unit-наборы: `permissions`, panel session policy, command parsing/serialization, voice policy, текстовые activity rules, баланс/валидация, идентификаторы и URL тыкв, state transitions, Matrix role guards, duration bounds, permission/hierarchy checks, queue и idempotency keys.

### Integration

С PostgreSQL проверять общие транзакции экономики, concurrent debit, покупки, начисление квестов, голоса, тыквы, Matrix start/snapshot/jail/unjail/restore, recovery и миграции. Использовать уникальную тестовую БД/схему и очищать её между прогонами без изменения dev/prod базы.

### Contract / Discord adapter

Проверять структуры slash-команд сериализатором Discord.js и адаптер Matrix на mock Discord API. Для каждой операции проверять вызовы, permission preflight, error mapping и частичный результат.

### End-to-end в тестовом guild

Выполнить минимум один полный путь пользователя для Economy, Hunt, Halloween, Pumpkin и Matrix, плюс отрицательный путь неавторизованного пользователя для каждой защищённой команды/кнопки.

### Требуемые покрытия

- 100% защищённых команд и component handlers имеют позитивный и негативный тест доступа.
- 100% денежных путей покрывают успех, недостаток средств/валидацию, повтор operation ID и конкурентный вызов.
- 100% внешних Discord mutation paths покрывают success, permission/hierarchy failure, missing resource и partial failure.
- 100% event state transitions имеют валидный путь, запрещённый переход и повторную доставку.
- Recovery сценарии покрывают каждый статус pending/partial/complete/skipped/failed из модели операции.

## 20. Условия приёмки релиза

Релиз может быть принят, если:

1. Все обязательные сценарии разделов 5–17 имеют `PASS`; `BLOCKED` и `NOT RUN` объяснены и согласованы.
2. Нет известного обхода `ADMIN_IDS`, владельца панели, фракционной проверки Matrix или подтверждения опасной операции.
3. Нет потерянных или повторно выданных конфет при retry/concurrency; финансовый ledger неизменяем при сбросе игровых данных.
4. Ни одна операция массовой смены ролей не объявляется полной при неполном результате; восстановление повторяемо.
5. Ни один бот или временная event роль не имеет Discord Administrator.
6. Миграции накатываются на чистую и предыдущую схему без потери данных.
7. Slash-команды успешно проходят schema validation и регистрируются на тестовом guild.
8. Сборка и typecheck проходят; полный `npm test` проходит в выделенной тестовой среде.
9. Итоговый отчёт содержит пройденные/проваленные тесты, найденные дефекты с severity, ID issue и ссылку на безопасные доказательства.

## 22. Покомандный каталог проверок и ожидаемых ответов

В этой части проверяется каждая зарегистрированная команда, подкоманда и административный префиксный маршрут. Указанный текст — контрольный формат текущего ответа; динамические значения (баланс, ID, дата, название) сверять с БД. Если проверяется отрицательный сценарий, дополнительно сверять отсутствие изменения данных. Для slash-команд, где обработчик ловит исключение, ожидается ephemeral-ответ с текстом ошибки сервиса; неожиданная техническая ошибка отображается как «Не удалось обработать команду. Попробуйте позже.» в Economy Bot и «Не удалось обработать команду.» в Event Master. Токены и внутренний stack trace пользователю не показываются.

### 22.1 Economy Bot: базовые slash-команды

| `/profile` | Embed «Профиль <username>», поля конфет и расы | Неизвестный профиль создаётся по правилам `getProfile`; DB failure не выдаёт ложные данные | Только свой профиль, ephemeral |

### 22.2 Economy Bot: способности

| Команда | Успешный ответ | Запрет/ошибка | Проверяемое изменение |
|---|---|---|---|
| `/bite player:@target` | `Укус успешен: украдено N 🍬.` | Не Vampire, self-target, недопустимая цель, нулевой баланс/кулдаун/повтор — ответ с EconomyError.message; проверить, что сумма не отрицательная | Списать у жертвы и начислить вампиру транзакционно; один interaction ID только один раз; ответ ephemeral |
| `/curse player:@target` | `Эффект действует до <locale date>.` | Не Witch, невалидная цель, Discord отказ выдачи роли — отказ/контролируемая ошибка; нет активного ложного эффекта | GameEffect на 1 час; если настроена curse role, проверить выдачу и recovery; ephemeral |
| `/possess player:@target` | `Эффект действует до <locale date>.` | Не Ghost, self/бот/невалидная цель, role hierarchy/permission failure — безопасное сообщение без stack | GameEffect на 30 минут, восстановление временной роли и сохранение её исходного состояния; ephemeral |

Для каждой способности выполнить 4 маршрута: правильная раса + допустимая цель; неправильная раса; невалидная/запрещённая цель; повтор/кулдаун или Discord API failure. Для ошибочного Discord mutation зафиксировать фактический ответ: если AbilityError не преобразован в дружественный текст, дефектом считается необработанный отказ Discord interaction.

### 22.8 Event Master: `/matrix`

Во всех admin-only подкомандах `USER` должен получить ephemeral `Эта операция доступна только администраторам бота.` и не менять данные. `/matrix jail`, `/matrix unjail` и кнопка «Продвинуть» в канале `#миссии` проверяются не по админскому allowlist, а по Matrix участию и роли.

| Команда | Успешный вывод | Отказы/граничные ответы | Проверяемые побочные эффекты |
|---|---|---|---|
| `/matrix list` | Список событий: название, ID, фаза, участники, миссии, состояние snapshot, counts operations | Пусто: `Событий «Судная ночь» пока нет.`; не-admin — admin denial | Только чтение; ограничение ответа <= Discord limit |
| `/matrix create title countdown_minutes [duration_hours ...]` | `Событие создано и ожидает запуска. ID: `ID`. Discord подготовил роли и категорию CATEGORY. Фракции будут случайно распределены между участниками сервера при запуске.` | Не в guild: `Создавать событие можно только на сервере.`; права provisioning/лимиты Discord — точная безопасная ошибка; не-admin denial | Отдельные роли/категория/каналы созданы и IDs сохранены; проверить нет дублей/лишних прав |
| `/matrix assign event_id player role [faction]` | `Предварительная роль сохранена. При запуске состав всех участников сервера будет случайно распределён заново.` | Неизвестное событие или event не на текущем guild: `Событие не найдено на этом сервере.`; неучастник/лимит/неверная роль — текст MatrixNightError; non-admin denial | Временная предварительная запись; при random start заменяется полным roster и случайными ролями |
| `/matrix start event_id` | `Подготовлен снимок состояния `SNAPSHOT_ID`. Фаза события: PHASE. Случайно распределено участников: N (Prophet: N, Punishers: N, Rebels: N, Prisoners: N).` При немедленной частичной выдаче в конце добавляется `Не удалось применить Discord-роль N участникам; результат записан для восстановления.` | Не на guild/неверный guild, неправильная фаза, плохие role permissions/Administrator, невозможный состав/нет участников, уже есть snapshot — MatrixNightError; не-admin denial | Ровно одна случайная faction на каждого текущего небот-участника; snapshot до Discord role mutation; журнал каждого apply/partial |
| `/matrix pause event_id` | `Событие приостановлено; оставшееся время сохранено.` | Не активное/неверное событие — MatrixNightError; non-admin denial | pausedAt/remaining duration сохраняются |
| `/matrix resume event_id` | `Событие продолжено. Фаза: PHASE.` | Не paused — `Событие не приостановлено.`; non-admin denial | Таймер продолжает оставшееся время |
| `/matrix emergency event_id outcome confirm:ОСТАНОВИТЬ` | `Событие аварийно завершено. Восстановлено: N; пропущено: N; ошибок: N. | `/matrix jail event_id player reason duration_minutes` | `Заключение записано до <Discord timestamp>. Статус: RESULT.`; duplicate: `Эта операция уже обработана.` | Не Punisher, не target/себя, jailed actor, неучастник, пустая причина, срок сверх config, неверный event/server — MatrixNightError | Запись MatrixJail + попытка роли Prisoner; проверять per-operation result |
| `/matrix unjail event_id player` | `Заключение завершено. Результат освобождения: RESULT.` | Не Rebel/нет активного jail/неверный event/server/jailed actor — MatrixNightError | Вернуть корректную игровую роль и зафиксировать результат |

### 22.9 Event Master: админские prefix-команды

Общие отрицательные ответы обработчика:

- Неизвестное имя после допустимого префикса: `Неизвестная команда. Используйте `<help`.`
- Пользователь не разрешён: `Недостаточно прав.`
- Неверные аргументы: `Неверные аргументы. Использование: <usage из таблицы>.`
- Неподдерживаемое сообщение/нет `<` или `>` в начале: игнорируется без ответа и мутации.

| Команда | Успех/вывод | Ошибки и проверки |
|---|---|---|
| `<help` / `>help` | Справка: `<help`, `<panel`, `<events`, `<event ...`, `<give`, `<take`, `<stats`, `<logs`; упоминается `>` alias | Лишний аргумент — usage; обычный пользователь — `Недостаточно прав.` |
| `<panel` | `Откройте `/panel`: Discord позволяет показывать панель только вам через скрытый ответ slash-команды.` | Лишние аргументы/не-admin отказ; не открывает панель напрямую |
| `<events` | В DM список `• TITLE — STATUS; ID: ID; окончание: UTC` (если задано); публично: `Отправил список N событий в личные сообщения.` | Нет событий: DM `Событий пока нет.` + N=0; DM закрыт — безопасный fallback; не-admin/лишние args — отказ |
| `<stats` | `События: N; участия: N; игроков: N; записей прогресса: N; загадки: N; квесты: N; тыквы: N; ошибки/отказы: N; награды: N.` | Лишний arg/не-admin/ошибка БД; только чтение |
| `<logs [count]` | DM последние N audit lines вида `UTC actor: action objectType/objectId result`; публично `Записи журнала отправлены вам в личные сообщения.` | Без count по умолчанию 10; 1..50; 0/51/нечисло/лишний аргумент — usage/error; пусто — `Журнал пуст.` |
| `<event start ID` | DM confirm `Подтвердите смену статуса события ID на «running».`; публично `Запрос подтверждения отправлен в личные сообщения.` | Ошибка синтаксиса показывает usage; cancel не меняет статус; confirm только тот же actor/session; состояние event валидируется |
| `<event pause ID` | Confirm статус `paused` | Те же проверки; нельзя подтвердить чужой/устаревший запрос |
| `<event resume ID` | Confirm статус `running` | Те же проверки; resume допустим только после pause |
| `<event end ID` | Confirm статус `ended` | Те же проверки; опасная операция без confirm не выполняется |
| `<give DiscordID amount` | DM confirm `Подтвердите выдачу N конфет у игрока ID.`; публично `Запрос подтверждения отправлен в личные сообщения.`; после confirm обновление панели отображает результат операции | Невалидный ID/amount/пользователь не найден/DM закрыт/отмена/недостаточный баланс не должен приводить к неверному начислению; не-admin отказ |
| `<take DiscordID amount` | DM confirm `Подтвердите снятие N конфет у игрока ID.` | То же; insufficient funds — отказ без отрицательного баланса |
| `<pumpkin` | `Откройте panel и выберите раздел «Тыквы».` | Лишние args/не-admin; команда только направляет в панель |
| `<riddle` | `Откройте panel и выберите раздел «Загадки».` | Лишние args/не-admin |
| `<quest` | `Откройте panel и выберите раздел «Задания».` | Лишние args/не-admin |
| `<reset` | Reset owner получает DM: `ВНИМАНИЕ: будут удалены профили, конфеты, история баланса, события, покупки, товары, настройки рас, эффекты и прогресс. Боты и команды останутся. Подтвердите действие кнопкой ниже.`; в канале `Запрос на сброс отправлен вам в личные сообщения для подтверждения.` | Не reset owner: `Недостаточно прав.`; недоступен DM — сброс не начинается; cancel: `Полный сброс отменён.`; после confirm проверять очистку ролей/каналов и данных. **Текущий warning прямо сообщает об удалении финансовой истории; это противоречит требованию её сохранить, поэтому подтверждённый reset — ожидаемый FAIL до исправления.** |

Для `<give`/`<take` подтвердить, что confirm/cancel принимается только владельцем соответствующей сессии, повтор кнопки не создаёт повторную операцию, а админское изменение баланса записывается в financial ledger и AuditLog.

### 22.11 Отчёт по каждой команде

В итоговом протоколе на каждую строку каталога выше поставить отдельные результаты для трёх колонок: `успешный путь`, `отказ/граница`, `повтор/восстановление`. Команда считается покрытой только если записан фактический текст ответа (или embed fields), visibility (ephemeral/DM/public), ID изменённых записей, ledger/AuditLog operation ID и результат повторного вызова. Если ожидаемый текст в документе расходится с кодом, это не исправлять молча в тестовом протоколе: оформить дефект документации или поведения и согласовать ожидаемый контракт.
